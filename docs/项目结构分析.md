# LQ_AICoding 项目结构分析

> 分析时间：2026-09-01
> 代码规模：`agent/` 下 47 个 Python 文件、11792 行；`ui/` Vue 3 前端；测试 12 文件 48 用例
> 结论先行：这是一个**教学目标导向的 AI Coding Agent 课程项目**，架构设计质量明显高于工程完备度。核心链路（安全边界、三层状态、跨平台）做得扎实，但测试、CI 覆盖面、文档同步三项尚未补齐。

---

## 一、这个项目在做什么

一句话：**让 AI Agent 在受控的本地工作区里读取代码、修改文件、跑命令验证、做代码审查，最后自动开 GitHub PR**——全程不允许越界访问宿主机器。

它的核心矛盾是"给 Agent 足够能力"与"防止 Agent 搞坏本机"之间的平衡，所以**安全设计是整个项目的主线**，而不是附加功能。

两种典型使用场景：
- **编码实施**：给一句需求 → Agent 克隆/定位仓库 → 实施方案 → 跑测试 → 提交分支 → 开 PR
- **只读审查**：给一个 PR 链接 → Reviewer 子 Agent 读 diff → 按规则逐文件审查 → 输出 finding 报告（禁止改代码）

## 二、整体分层

```
Vue 3 前端 (ui/)
      ↓ REST + SSE
API 层 (agent/api/)  ——  /dashboard/api/*（前端）与 /api/*（运维）
      ↓
编排层 (agent/core/)  ——  runtime.py 决策 · streaming_runtime.py 执行
      ↓
Agent 层 (agent/server.py + middleware/)  ——  DeepAgents 组装 · 6 层中间件 · 2 个子 Agent
      ↓
能力层 (agent/backends/ + tools/)  ——  LocalShell 沙箱 · 10 个工具 · permissions 校验
      ↓
状态层 (data/*.sqlite)  ——  业务 Store · Checkpoint · 长期记忆
```

### 一次请求的完整路径

```
前端 POST /dashboard/api/threads/{id}/stream-message (SSE)
  → dashboard_routes.py 建线程、归一化仓库地址
  → runtime.run_agent_task()
      ① 列举工作区 / git pull（纯本地，不调模型）
      ② classify_task_kind() 意图分类（关键词快通道 → 模型 → 关键词兜底）
      ③ 安全阀 _apply_security_guard()：用户说"只审查"时强制把 coding 降级
      ④ coding 任务若无已确认方案 → 强制转 planning（人在回路）
      ⑤ 用户确认后从 checkpoint 回溯 plan 的 source_prompt，还原原始需求再切回 coding
  → streaming_runtime.run_agent_with_event_stream()
      消费 stream_events(v3)，解析 text-delta / tool_calls / subagents
      从未闭合的 JSON args 片段里正则提取 write_todos 清单
  → 结果落 Store（threads / runs / run_events），成功后写回仓库记忆
```

## 三、各模块职责详解

### 3.1 服务入口 `agent/app.py`

FastAPI 入口，模块级执行 `load_environment()` + `configure_logging()`，只挂 CORS 中间件（白名单 3000/5173），注册两组路由。

⚠️ **没有 lifespan 生命周期管理**——checkpointer 与 Store 靠 `graph.py` 里的模块级全局变量懒加载，进程级复用，无优雅关闭。

### 3.2 `agent/server.py`（469 行）— Agent 组装工厂

**名字有严重误导性：它不含任何 HTTP 端点**，真正的路由全在 `agent/api/`。它对外只暴露 `get_agent(config)`。

核心是 `create_deep_agent(...)` 调用：

| 组装项 | 内容 |
|---|---|
| 子 Agent | `general-purpose`（只读 `/projects`，仅可写 `/reviews`、`/tmp`）；`code_reviewer`（绑 6 个 review 工具，禁改源码/提交/PR） |
| 权限 | 声明式 `FilesystemPermission`——**只有 `task_kind == "coding"` 才放开 `/projects` 写权限** |
| 工具分发 | 8 个只读/中性工具常驻；`open_github_pull_request` + `publish_github_pr_comment` **仅 coding 任务注册** |
| Backend | `CompositeBackend(default=LocalShellBackend, routes={"/memories/": StoreBackend})`，按 thread 复用 |
| 模型 | `make_main_model` → DeepSeek `deepseek-v4-pro`（temperature 1.1 / max_tokens 25600 / 关思考模式）；`make_intent_model` → temperature 0 / max_tokens 200 |

### 3.3 编排层：runtime vs streaming_runtime

这是最容易混淆的两个大文件，分工是：

- **`runtime.py`（1243 行）= 产品流程控制**，决定"跑什么"：任务分派、意图分类、方案确认、状态落库、记忆写回。
- **`streaming_runtime.py`（1042 行）= 执行与序列化**，决定"怎么跑、怎么吐"：消费 LangGraph 事件流、解析增量文本、节流刷出。

两者通过 `event_sink` 回调与 `run_id` 解耦，runtime 不碰 HTTP 与事件解析，streaming 不做任务决策。

**亮点**：coding 任务必须先出方案等用户确认，这个"人在回路"是**在代码层强制实现的，而不是靠提示词约束**——模型无法通过嘴硬绕过。

### 3.4 中间件链（执行顺序即调用链，见 `server.py:431-438`）

| # | 中间件 | 解决的问题 |
|---|---|---|
| 1 | `MessageSanitizeMiddleware` | 发给模型前清洗消息：丢弃非文本 content block、剔除无匹配 ToolMessage 的孤儿 tool_call，防 OpenAI 协议报错 |
| 2 | `ContextInjectionMiddleware` | 整轮只注入一次仓库记忆为 SystemMessage（截断 6000 字） |
| 3 | `SanitizeToolInputsMiddleware` | 工具入参清洗：绝对路径→虚拟路径、拦 `..` 越界与 `.secrets`、GitHub URL 脱敏 token、写工具硬编码兜底规则 |
| 4 | `create_summarization_tool_middleware` | DeepAgents 内置，长工具输出自动摘要 |
| 5 | `ModelCallLimitMiddleware(run_limit=500)` | 防模型调用死循环 |
| 6 | `ToolErrorMiddleware` | 兜底捕获工具异常，转带 `error_type/hint` 的结构化 ToolMessage 并回写前端 run_events |

⚠️ 另外两个文件的情况：`run_limits.py` **根本没有 `RunLimitsMiddleware` 类**，只有 `AgentRunLimitTracker`，由 streaming_runtime 直接实例化使用；`memory_update.py` 的 `MemoryUpdateMiddleware` 定义了但从未注册。

### 3.5 能力层：`agent/backends/`（安全核心）

**`local_shell.py`（1191 行）** — 继承 `BaseSandbox` 的受控本地后端。

- **虚拟路径映射**：`/projects`、`/skills`、`/policies`、`/reviews`、`/runtimes`、`/tmp`、`/logs`，另有隐式 `/secrets`。模型只能看到虚拟路径，**宿主真实路径不暴露**。
- **边界校验**：`_resolve_virtual_path()` 拼到 root 后 `.resolve()`，再校验 `relative_to(root)`。
- **文件操作**：`ls/read/write/edit/glob/grep/upload/download`。`write` 要求文件不存在（改文件必须用 `edit`），`edit` 多处匹配需 `replace_all`。
- **写保护**：`policies/skills/runtimes/logs/secrets` 全部禁止写入，只有 `/projects` 下可写。
- **命令执行**：三层校验（只读模式 → `_deny_reason()` 粗粒度拒绝 → `normalize_safe_command()` 白名单）→ 虚拟路径替换 + git askpass 注入 → `subprocess.run`。
- **Token 安全**：通过 `GIT_ASKPASS` 环境变量注入凭据（不进命令行参数），`_mask_token()` 在日志与返回值中替换为 `***`。
- **跨平台**：初始化强校验 `LOCAL_SHELL_PLATFORM == 实际平台`；venv 目录 `bin/` vs `Scripts/`；askpass 生成 `.sh`(chmod 700) vs `.cmd`；编码 macOS 用 utf-8、Windows 取系统代码页。

**`permissions.py`（119 行）** — 纯函数安全收敛层。

- `assert_path_inside()`：`resolve()` 后比较 parents 链防穿越
- **命令白名单**：`git/git.exe/pytest/ruff/java/javac`、`python/python.exe/python3/py/pip/pip3`、`ls/cat/which/pwd/clear/test`、`dir/type/where/cd/cls`
- **shell 操作符全禁**：`&& || | & ; > < \` $( \n \r`（先剥掉尾部 `| tail -N` 和 `2>&1` 再检查）
- 危险片段黑名单：`format`、`shutdown`、`rm -rf`

**`workspace.py`（41 行）** — 极简封装，root 相对路径解析 + 边界断言，构造时 `mkdir`。

### 3.6 工具层 `agent/tools/`（对外导出 10 个工具）

| 文件 | 职责 |
|---|---|
| `github_api.py` | httpx 封装：建 PR（422 时查同 head/base 的 open PR 并复用）、发评论、读 PR commits/files/行级评论。Token 按 `GITHUB_TOKEN → GH_TOKEN → SCM_GITHUB_TOKEN` 取，仅放 Header，错误文本全部脱敏 |
| `github_tools.py` | 3 个 `@tool`。前两个（开 PR、发评论）在只读任务下**直接拒绝** |
| `safe_http.py`（308 行） | SSRF 防护，实现扎实：只允许 http/https → `getaddrinfo()` 逐个 IP 拦截私有/环回/链路本地/保留地址 → **DNS Pin**（monkey-patch urllib3 的 `create_connection` 直连已校验 IP，防 DNS rebinding，带引用计数与全局锁）→ 自管重定向每跳重新校验，最多 5 跳 |
| `web_search.py` | 智谱 `search_pro` 联网搜索，固定 count=3，SDK 懒加载（优先 `zai`，回退 `zhipuai`） |
| `fetch_url_tools.py` | 抓网页转 Markdown，优先 `markdownify`，回退自写提取器（跳过 script/style），正文截断 20000 字符 |
| `reviewer_diff.py` | 确定性 diff 解析。`_SAFE_GIT_REF_RE` 防模型把 shell 片段塞进 `git diff` 参数；从 `@@ +N` 起算新文件行号；`validate_finding_location()` 校验 finding 行号必须命中真实新增行 |
| `reviewer_tools.py` | 5 个审查工具：加载规则、读 diff、校验 finding 位置、添加 finding（severity 白名单）、列出 findings |
| `runtime_context.py` | 从 LangGraph config 读 `thread_id` / `task_kind`，供工具判断写权限 |

### 3.7 状态层：三种状态必须分清

这是项目里最容易踩坑的地方，**三个 SQLite 库各管一段，不能混用**：

| 数据库 | 管理者 | 用途 | 现状 |
|---|---|---|---|
| `data/store.sqlite` | `LocalSqliteStore` | **产品页面数据**，9 张表：threads / runs / run_events / thread_messages / thread_plans / review_findings / settings / repo_workspace_mappings / repo_memories | threads 3 行、runs 8 行、run_events 62 行，其余为空 |
| `data/checkpoints.sqlite` | LangGraph `SqliteSaver` | **对话恢复**，checkpoints + writes 两张表 | 5.6MB，checkpoints 575 行 |
| `data/langgraph_store.sqlite` | LangGraph Store | **跨会话长期记忆**，按 namespace 存仓库记忆 | 24KB，store 表 1 行 |

全部写入采用 `IF NOT EXISTS` + `threading.Lock` + `ON CONFLICT DO UPDATE` 幂等 upsert，`_ensure_column()` 做轻量增量迁移。

**记忆机制**（`repo_memory.py` / `repo_memory_update.py`）：
- 寻址：`namespace=("lq-aicoding","repo-memory",owner,repo)`，虚拟路径 `/memories/{owner}/{repo}.md`
- 更新是**纯字符串结构化提炼，不调 LLM**——按章节覆盖技术栈/启动/测试命令，追加结论（上限 20 条）
- `SENSITIVE_MARKERS` 命中 `.env/api_key/私钥` 直接跳过，防止敏感信息进入长期记忆

### 3.8 API 路由

**`routes.py`**（无前缀，运维向）：
`GET /health`、`POST /api/tasks`、`GET /api/tasks`、`GET /api/tasks/{id}`、`GET /api/logs/backend`、`GET /api/logs/agent`

**`dashboard_routes.py`**（前缀 `/dashboard/api`，服务前端）：
`GET /me`、`/options`、`/threads`、`/threads/{id}`、`POST /threads/stream-message`、`POST /threads/{id}/stream-message`（**SSE 主链路**）、`DELETE /threads/{id}`

会话正文是**从 LangGraph checkpoint 读的，不是从 Store 读的**——`checkpoint_history.py` 是前端历史的唯一来源，用 `sha1(作者+正文)` 去重生成稳定 `message_id`。

### 3.9 前端 `ui/`

Vue 3.5 + Vite 7 + Pinia 3 + axios + markdown-it + DOMPurify。无 TypeScript、无 vue-router、无 UI 组件库。

| 文件 | 职责 |
|---|---|
| `src/api/sse.js`（75 行） | **手写 SSE 解析**（fetch + ReadableStream + TextDecoder，按 `\n\n` 切块），没用 EventSource，因为要发 POST |
| `src/stores/agent.js`（297 行） | Pinia 核心：bootstrap、会话 CRUD、流式事件归并 |
| `components/AgentWorkspace.vue` | 三栏主布局 |
| `components/SessionSidebar.vue` | 会话列表、新建、删除 |
| `components/ChatComposer.vue` | 输入框 + 仓库地址 + 模型/effort 选择 |
| `components/ChatMessage.vue` | Markdown 渲染（DOMPurify 防 XSS）+ todo/error chunk |

消费 8 类 SSE 事件：`thread_snapshot`、`user_message`、`todo_delta`、`message_start`、`text_delta`、`error`、`done`、`thread_done`。

### 3.10 Skills（`agent/skills/`）

三个 SKILL.md 是给 Agent 看的操作规程，质量不错：

- **ai-coding-implementation**（148 行）：三阶段——定位约束确认 → 聚焦实现与最小验证 → Git 收尾与 PR
- **code-review**（216 行，最完整）：8 步固定流程，明确"只审不改"（禁改代码、禁 commit/push、禁建 PR），含报告模板与结论判断标准
- **repo-bootstrap-analysis**（108 行）：陌生仓库首次分析，建立项目画像

配套 `reviewer_rules/default_review_rules.md`（76 行）9 节中文规则，含 5 级严重度定义表。

## 六、安全机制总评：三道防线

```
第一道：声明式 permissions —— 只有 coding 任务放开 /projects 写；只读任务连 PR 工具都不注册
第二道：中间件清洗      —— SanitizeToolInputs 拦截路径越界、token 泄露；意图分类器有负向词安全阀
第三道：LocalShellBackend 兜底 —— 命令白名单 + shell 操作符全禁 + 路径边界校验 + askpass 认证 + 输出脱敏
```

`.workbuddy/memory/` 里的实测记录证实三道防线有效：`cat ../.env`、`cat /etc/hosts`、`rm -rf` 均被拦截。

**但仍有缺口：**
- `get_review_diff_summary` 内部**自建 `LocalShellBackend()`** 而非复用运行时注入的 backend，绕过了统一权限边界（与其自身文档的自我要求相悖） **[状态：⏳ 待处理：高风险改动，待评估]**
- `permissions.py` **只校验命令首词，无参数级过滤**——`python -c "..."`、`git` 任意子命令均可放行 **[状态：⏳ 待处理：安全策略升级，待定范围]**
- `execute()` 的 `truncated` 字段**恒为 False，输出截断是空壳**，超长命令输出会直接撑爆模型上下文 **[状态：✅ 已修复：新增 `_truncate_shell_output()` 真实截断]**
- `glob()` 全目录 `rglob` 且无结果数上限，会扫进 `.venv`、`.git` **[状态：✅ 已修复：改用 `os.walk` 跳隐藏/系统目录，结果上限 5000]**
- 无容器/系统级隔离，README 与代码注释均自述为"开发级安全边界"
